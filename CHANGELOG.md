# Changelog

## [Unreleased]

### Added — 2026-11-12
- M4b: регрессионные тесты семи выживших мутантов (OC02–OC05, IM02, LM03,
  LG03); проверка размера и пикселей PNG не допускает снимок всей страницы
  вместо картинки CAPTCHA.
- M4b: текстовое задание SmartCaptcha решается через vision LLM за максимум
  три раунда: PNG-скриншот загруженной картинки, OCR, нормализация регистра и
  пробелов, ввод с key-событиями, ожидание токена или нового отказа. Старая
  подсказка не считается новым отказом; следующий раунд ждёт смены картинки.
  Сбой OCR обновляет задание, выключенный LLM даёт явную ошибку без submit.
  Общий дедлайн опроса увеличен до 75 с и ограничивает также OCR с отменой CLI.
- Vision LLM: `read_text` с отдельной JSON-схемой `text` и разбором объекта из
  запасного текстового ответа; схема `indices` и флаги песочницы сохранены.
  Временная картинка удаляется и при ошибке, в логах только длина ответа.
- Offline-тесты M4b проверяют раунды в Chromium, задержанные картинку и токен,
  сбои/отключение OCR, ленивую инициализацию, схемы CLI, отсутствие текста в
  stdout/stderr и отмену OCR по дедлайну. В M4a `test_Y4_text_challenge` теперь
  проверяет явную ошибку выключенного LLM вместо прежнего `not supported`.
- SmartCaptcha: ранний клик по уже видимой кнопке может теряться до готовности
  виджета. Клики и протяжки повторяются через 5 с без токена или задания, с общим
  лимитом 4 действия. Невидимый режим вызывает `execute()` один раз, не раньше
  чем через 3 с после загрузки, чтобы дождаться возможного появления чекбокса.
- Offline-тесты воспроизводят потерянный ранний клик, четыре безрезультатные
  попытки, отложенный `execute()` и появление checkbox-iframe через секунду.

- Тип задачи `yandex_smartcaptcha`: рендер виджета, чекбокс, протяжка слайдера и
  невидимый режим с возвратом токена. Дедлайн 60 с ограничивает каждый запрос к
  странице; текстовые задания и силуэты пока завершаются понятной ошибкой (M4b).
- Необязательный `proxy`: публичные HTTP/HTTPS/SOCKS5 (SOCKS5 без авторизации),
  проверка всех адресов DNS, закрепление проверенного IP и отдельный контекст
  браузера с закрытием вместе со страницей. Ошибки разбора не раскрывают пароль.
- Удаление `proxy` из БД при `solved`/`failed`, включая восстановление прерванных
  задач. Offline-тесты Chromium проверяют механику виджета, прокси, API и дедлайн;
  opt-in e2e проверяет официальную демку Яндекса.
- Короткий бюджет клика/протяжки: не больше 5 с и остатка общего дедлайна; все
  этапы протяжки делят один бюджет. После действия, включая таймаут, снова
  проверяется токен. Ошибка первого mouse.move учитывается в лимите и паузе.
  Текст ошибки использует фактический `DEADLINE_SECONDS`.
- Создание прокси-контекста защищено от отмены; если задача отменена, контекст
  закрывается по завершении создания; остановка менеджера дожидается отложенной
  очистки.
- `tests/test_m4a_gaps.py`: проверки 11 выживших независимых мутантов, отмены
  создания контекста, зависших действий и ошибки первого движения слайдера.
- README описывает хранение пароля прокси открытым текстом до завершения задачи
  и возможное сохранение секрета в WAL, свободных страницах и резервных копиях.

### Fixed — 2026-11-12
- SmartCaptcha: `_challenge_kind` один раз получает видимый iframe как
  ElementHandle и его content_frame, затем проверяет корень и читает класс
  через этот frame под общим дедлайном. Скрытие iframe между count и чтением
  класса больше не блокирует опрос уже выданного токена. Новый тест управляемо
  воспроизводит эту гонку; фейки M4a используют query_selector/content_frame,
  сохраняя проверку отсутствующего корня и ограничений опроса.
- SmartCaptcha: последний обработанный src сохраняется только после успешного
  submit или клика refresh. Однократный сбой очистки поля, ввода, submit или
  refresh больше не заставляет повторный вход ждать несуществующую новую
  картинку; общий бюджет OCR-раундов при этом сохраняется. Регрессионные тесты
  проверяют повтор того же src и фактическое число submit/refresh.
- SmartCaptcha: ожидание загруженной новой картинки продолжает проверять токен
  и скрытие iframe; поздний токен после 10-секундного окна исхода не теряется.
  Бюджет раундов и последний обработанный src сохраняются в контексте опроса
  при повторном входе после ошибки Playwright, а новая задача получает новый
  бюджет. Ошибка скриншота до вызова OCR не расходует дополнительный раунд.
- Тип задания и текстовый решатель выбирают видимый advanced-iframe, включая
  второй iframe после повторного клика. Решатель привязан к выбранному элементу:
  скрытие iframe между запросами больше не блокирует чтение токена.
  `OUTCOME_WAIT_SECONDS = 10` задаёт окно
  исхода; число раундов в ошибке берётся из `MAX_TEXT_ROUNDS`.
- Vision LLM: каждый вызов CLI получает уникальный файл схемы, который удаляется
  в `finally` при успехе, ошибке и отмене. Параллельные OCR и классификация
  плиток больше не перезаписывают схемы друг друга. Выключенный классификатор
  обозначается `VisionLLMDisabledError` (подкласс `RuntimeError`); слово
  `disabled` в посторонней ошибке CLI больше не прерывает текстовый решатель.
- `test_T5_llm_disabled` использует типизированную ошибку. Тесты новых границ
  раундов проверяют фактическое число в сообщении, а проверки скрытия iframe
  и исчезающей подсказки отличают корректный выход от позднего чтения токена.
- Счётчики submit/refresh в gap-фикстуре читаются из iframe, где произошло
  действие, без гонки с доставкой `postMessage`; задержанная доставка отдельно
  воспроизводится в тесте отказа по новой подсказке.

### Removed — 2026-11-12
- Удалён нерабочий `workers/solvers/yandex.py` и его регистрации в unified API;
  прежняя запись о «full implementation» Yandex CAPTCHA/SmartCaptcha была неверной.

## [1.2.1] - 2026-11-11

### Fixed
- Turnstile: клик мышью по чекбоксу ограничен по времени: `CLICK_TIMEOUT` 5 с, но
  не дольше остатка дедлайна опроса (с тем же минимумом 0,5 с, что у
  `page.evaluate`). Зависший клик больше не держит опрос токена: он отменяется, в
  лог идёт предупреждение, попытка не засчитывается.
- Vision LLM: остановка зависшего `qwen` не падает на `PermissionError` от
  `process.kill()` (как уже было для `os.killpg`) и всё равно дожидается
  `process.wait()` с ограничением по времени.
- Vision LLM: текст ответа модели (рассуждения, первая строка вывода, «сырой»
  ответ) больше не пишется в лог — только длина текста и число выбранных плиток.
  Ответ формируется по картинке со страницы атакующего.
- Vision LLM: строка из ответа модели вроде `"²3"` (`str.isdigit()` истинно, `int()`
  падает) отбрасывается, а не поднимает `ValueError` с этой строкой в тексте.

### Known limitations
- reCAPTCHA v2 на реальных сайтах с датацентрового IP: на демо Google (11.11, 1.2.0,
  vision LLM включён) за две задачи Google не принял ни одного раунда из девяти, обе
  упали по общему таймауту задачи 120 с. Динамический раунд занимает 20–60 с (вызов
  классификатора 7–12 с), поэтому пять раундов в 120 с не укладываются. Тестовый ключ
  Google и чекбокс без челленджа работают.

## [1.2.0] - 2026-11-11

### Added
- Режим «виджет» для браузерных солверов: необязательное поле `render_mode` в
  `input_data` (`page` — по умолчанию, `widget`). В режиме `widget` воркер не
  грузит сайт клиента: первая навигация главного фрейма (это `goto(page_url)`
  солвера) перехватывается `page.route`, и вместо неё отдаётся минимальная
  страница с виджетом провайдера и `site_key`; остальные запросы идут дальше
  через `route.fallback()`, а после выдачи страницы обработчик снимается. Origin в запросе к провайдеру
  остаётся прежним, поэтому режим решает задачу и тогда, когда сайт закрыт от IP
  воркера WAF-ом (публичные демо-страницы отвечают датацентру 403), а скрипты
  провайдера доступны.
- Общий модуль `workers/solvers/widget_page.py`: `check_browser_input`
  (единый контракт входа — `site_key` 1–100 символов `[A-Za-z0-9_-]`,
  `page_url`, `render_mode`), `widget_html` (шаблоны turnstile, hcaptcha,
  recaptcha_v3 и recaptcha_v2 — последний для вехи M3b, солвер v2 его пока не
  использует) и `install_widget_page`.
- `tests/test_m3a_unit.py` — 37 тестов (U1) без сети: отказ на пустых полях и на
  `site_key` с `"`, `<`, пробелом или длиной 101, на `render_mode="iframe"`;
  приём тестовых ключей всех трёх провайдеров в обоих режимах; содержимое
  `widget_html`; предикат маршрута; скрытие токена в логе воркера.
- `tests/test_m3a_e2e.py` — 6 тестов (E1–E6) против тестовых ключей провайдеров,
  только при `ANTICAPTCHA_E2E=1`. Солверы вызываются как в воркере (класс из
  `SOLVERS`, `setup()`/`solve()`/`cleanup()`), `page_url="https://example.com/"`,
  `render_mode="widget"`. Замер в образе `anticaptcha:m2-accept`: 6 passed за
  50,9 с (E1 2,4 с; E2 30,5 с; E3 8,9 с; E4 1,2 с; E5 5,5 с; E6 0,4 с).
- reCAPTCHA v2 (`RecaptchaV2Solver` в `workers/solvers/recaptcha.py`) решает
  картиночный челлендж раундами: `_solve_rounds` повторяет «прочитать челлендж
  → выбрать плитки → нажать `#recaptcha-verify-button`» до токена, не больше
  `MAX_ROUNDS = 5` раундов. `_wait_round_outcome` после verify до 10 с
  различает три исхода: `token` (непустой `#g-recaptcha-response`), `retry`
  (виден `.rc-imageselect-error-select-more`,
  `.rc-imageselect-error-dynamic-more` или `.rc-imageselect-incorrect-response`,
  либо Google подменил инструкцию/сетку) и `timeout`. Нет исхода —
  `RuntimeError("reCAPTCHA v2: no outcome after verify")`, раунды кончились —
  `RuntimeError("reCAPTCHA v2: challenge not solved in 5 rounds")`.
- `_read_challenge` читает челлендж со страницы: цель — текст `<strong>` внутри
  `.rc-imageselect-desc-wrapper` / `.rc-imageselect-instructions` (нет
  `<strong>` — целью считается вся инструкция), сетка — по числу
  `.rc-image-tile-wrapper` (9 → `3x3`, 16 → `4x4`), признак динамической сетки —
  по `none left` в инструкции. Все помощники челленджа принимают «корень»,
  объект с методом `.locator()`: в бою это
  `page.frame_locator('iframe[src*="bframe"]')`, в тестах — страница с поддельным
  DOM bframe.
- Динамическая сетка («Click verify once there are none left»):
  `_clear_dynamic_grid` кликает выбранные плитки, ждёт смены `src` их картинок
  (до 5 с, иначе запись в лог) и выбирает заново, пока выбор не пустеет, — не
  больше `MAX_DYNAMIC_PASSES = 5` проходов; затем verify (исчерпание лимита с
  непустым выбором тоже пишется в лог).
- Раунды v2 после ревью: снимок челленджа включает адреса картинок плиток
  (новая сетка с прежней инструкцией — `retry`, а не `timeout`) и берётся перед
  самым verify; баннер ошибки, видимый до verify, считается исходом, только
  если пропал и появился снова. Каждый вызов страницы в опросах ограничен
  остатком времени до дедлайна (не меньше 0,5 с), так что 6 и 10 с соблюдаются
  и при зависшем JS. Уже выбранные плитки повторно не кликаются, повторы
  индексов от классификатора отбрасываются. Цель для локального фолбэка
  приводится к имени класса (`fire hydrants` → `fire_hydrant`, `buses` → `bus`).
- `tests/test_m3b_contracts.py` — тесты без сети на границы раундовой логики и
  на выживших мутантов независимого прогона.
- `recaptcha_v2` принимает `render_mode` через общий `check_browser_input` и в
  режиме `widget` отдаёт свою страницу виджета (`install_widget_page(page,
  page_url, "recaptcha_v2", site_key)`) — шаблон, добавленный в M3a, теперь
  используется.
- `tests/test_m3b_unit.py` — 6 тестов (B1–B6) без сети, на поддельном DOM bframe
  в Chromium из образа: кроп плитки из спрайта, два раунда, `error-select-more`,
  динамическая сетка, исчерпание раундов, чтение цели и сетки 4x4.
  Классификатор — заглушка, ключа vision LLM в образе нет. Замер в
  `anticaptcha:m2-accept`: 6 passed за 13,95 с (B4 5,78 с; B2 2,01 с; B5 1,53 с;
  B3 1,32 с; B1 1,02 с; B6 0,46 с). Полный сьют без сети: 276 passed, 7 skipped
  за 46,9 с (на BASE `209578b` — 270 passed, 6 skipped за 35,6 с).
- `tests/test_m3b_e2e.py` — 1 тест (E7), только при `ANTICAPTCHA_E2E=1`:
  тестовый ключ Google, `page_url="https://example.com/"`, `render_mode="widget"`
  → токен не короче 100 символов. Замер: токен 1636 символов за 4,8 с
  (повторный прогон — 1657 символов за 4,9 с; длину выдаёт Google). Раунды
  челленджа в e2e не проверяются: для них нужен ключ vision LLM, а на тестовом
  ключе Google челлендж не выдаётся.

### Fixed
- Режим `widget` молча не срабатывал, если Chromium менял URL навигации
  (`:443` убирается, кириллица в пути кодируется, `%2e%2e` схлопывается):
  предикат сравнивал URL с `page_url` буквально, и грузился сайт клиента.
  Теперь подменяется первая навигация главного фрейма без сравнения URL;
  `widget_route_matcher` удалён. E2E: `:443` и Unicode-путь с `%2e%2e`.
- Опрос токена Turnstile/hCaptcha и ожидание `grecaptcha.execute` v3 не
  ограничивали сам `page.evaluate`: при зависшем JS страницы дедлайны 30/20/5 с
  не действовали. Каждый вызов — под `asyncio.wait_for` с остатком до дедлайна
  (не меньше 0,5 с; одиночная проверка v3 — 2 с).
- Turnstile: контейнер ниже экрана не получал клика — перед замером бокса он
  прокручивается в центр (`scrollIntoView`). Фрейм провайдера определяется по
  hostname (`challenges.cloudflare.com`), а не подстрокой URL.
- `check_browser_input`: `site_key` с завершающим `\n` принимался
  (`match` + `$`), теперь `fullmatch`. `render_mode` по умолчанию `page` только
  при отсутствии ключа или `null`; `false`, `0`, `[]`, `""` и прочие нестроковые
  значения — `ValueError`.
- `tests/test_m3a_contracts.py` — тесты без сети на граничные значения и
  дедлайны (виртуальные часы), выжившие в независимом мутационном прогоне.
- Turnstile (`workers/solvers/turnstile.py`): iframe виджета теперь в закрытом
  shadow DOM, поэтому CSS-селектор `iframe[src*="challenges.cloudflare.com"]`
  его не видел и `wait_for_selector` висел 60 с, хотя токен уже лежал в
  `input[name="cf-turnstile-response"]` (light DOM). Ожидание по селектору
  убрано: токен опрашивается каждые 0,5 с (hidden input, затем
  `turnstile.getResponse()`) с общим дедлайном 30 с, а на 8-й, 14-й и 20-й
  секунде — не больше трёх попыток за задачу — выполняется клик мышью по
  координатам контейнера (~30 px от левого края, по вертикальному центру):
  интерактивный виджет выдаёт токен только после настоящего клика. Клик
  пропускается, если фрейма `challenges.cloudflare.com` ещё нет в `page.frames`
  или у контейнера нулевой box. Нет токена к дедлайну —
  `RuntimeError("Turnstile token not received within 30s")`. Замер: ключ
  `1x…AA` → `XXXX.DUMMY.TOKEN.XXXX` за 2,4 с; `3x…FF` → тот же токен за 8,9 с
  (с мутацией «клик не выполняется» — `RuntimeError` через 30 с); `2x…AB` →
  `RuntimeError` через 30,5 с.
- hCaptcha (`workers/solvers/hcaptcha.py`): `iframe[src*="hcaptcha"]` матчит два
  фрейма — checkbox и challenge, — из-за чего клик падал в strict mode violation
  (замер: `resolved to 2 elements`), а селектор `.checkbox` не находил элемент
  `#checkbox`. Селектор закреплён модульной константой
  `CHECKBOX_FRAME = 'iframe[src*="frame=checkbox"]'` (замер: 1 совпадение),
  фиксированный `sleep(3)` заменён опросом `[name=h-captcha-response]` /
  `hcaptcha.getResponse()` каждые 0,5 с до 20 с. `NotImplementedError` убран:
  интерактивный image-челлендж не поддерживается и задача падает с
  `RuntimeError("hCaptcha token not received within 20s (interactive challenge
  is not supported)")`. Замер: тестовый ключ `10000000-ffff-…` →
  `10000000-aaaa-bbbb-cccc-000000000001` за 1,2 с.
- reCAPTCHA v3 (`RecaptchaV3Solver` в `workers/solvers/recaptcha.py`): работал,
  только если страница сама грузила `api.js?render=<key>`, иначе
  `ReferenceError: grecaptcha is not defined`, а ожидание `grecaptcha.ready`
  вообще не было ограничено. Теперь: до 5 с ждём `grecaptcha.execute` от страницы
  (второй экземпляр `api.js` не внедряется — два объекта `grecaptcha` затеняют
  друг друга), затем `add_script_tag` и ожидание `execute` — оба шага под одним
  `asyncio.wait_for(..., 15)` (`add_script_tag` сам ждёт загрузки скрипта и без
  ограничения висит на зависшей загрузке), а `grecaptcha.ready` + `execute` — под
  `asyncio.wait_for(..., 20)`. Ошибки JS и таймауты превращаются в `RuntimeError`
  с коротким текстом `reCAPTCHA v3: …` без стека Playwright. Замер: на
  `example.com` без `api.js` и с подменённым скриптом Google токен получен за
  5,5 с; с мутацией «инъекция отключена» — `RuntimeError` вместо токена.

- Лог воркера больше не печатает токен задачи: строка «solved» выводит

  а короткие значения (ответ `image_text`) остаются как есть. В базе
  `task.result` сохраняет настоящий токен — клиент его получает. Замер: токен из

  (`tests/test_m3a_unit.py`).
- `RecaptchaV2Solver` больше не печатает часть токена: строка

### Known limitations
- `_reap` шлёт `killpg` по сохранённому номеру PID лидера. Когда группа
  целиком умерла и собрана, номер свободен, и Linux может выдать его заново:
  если до нашего `killpg` его получит новый лидер группы, SIGKILL уйдёт этой
  чужой группе. Для этого счётчик PID должен обернуться через `pid_max` за
  время между смертью группы и вызовом `killpg` — окно ничтожное, но не
  нулевое.

### Fixed
- Оценка места перед разовой миграцией `VACUUM` (`_has_room_for_vacuum`)
  учитывает страницы в `-wal` и свободное место во временном каталоге SQLite
  (`SQLITE_TMPDIR`, `TMPDIR`, `/var/tmp`, `/usr/tmp`, `/tmp`): временная копия
  может лежать на другом разделе.
- Миграция `tasks` на AUTOINCREMENT не трогает `sqlite_autoindex_*`
  (индексы UNIQUE/PRIMARY KEY нельзя удалить через `DROP INDEX`).
- qwen CLI запускается в отдельной сессии (`start_new_session=True`), а при
  таймауте и отмене `_reap()` убивает всю группу процессов (`killpg`) и ждёт
  завершения не дольше `_REAP_TIMEOUT` (5 с). Раньше `await process.wait()`
  после `kill()` мог висеть бесконечно: в Python 3.11 он ждёт и закрытия pipe'ов,
  а их держат потомки node-процесса.
- Воркер на свежем томе создаёт таблицы сам: `init_db()` первым шагом `run()`.
  Раньше при ещё не стартовавшем API воркер падал с `no such table: tasks`.
- Сбой `recover_interrupted_tasks()` больше не роняет воркер: пишется
  `⚠️ Recovery of interrupted tasks failed: <тип>: <текст>` и работа
  продолжается. Флаг `_recovery_pending` снимается только успехом, и цикл
  воркера повторяет попытку на каждой итерации — раньше ошибка восстановления
  глоталась навсегда, и задачи в `processing` висели до следующего рестарта.
- Версия берётся из `app.__version__` (`FastAPI(version=…)` и ответ `/`) и
  совпадает с `appVersion` чарта — 1.0.1; раньше в `app/main.py` было
  захардкожено 1.0.0.
- `PIL.Image.open` в процессе воркера подменён обёрткой ultralytics, которая
  глушит исходную ошибку и бросает `ModuleNotFoundError: No module named
  'pi_heif'` (и пытается поставить пакет в рантайме). Проверка размеров читает
  заголовок исходной функцией Pillow, поэтому бомба распознаётся как
  `Image too large:`, а не как `Unsupported or corrupt image`.
- `is_fresh()` в `workers/heartbeat.py` больше не считает свежей метку `inf`,
  `nan` или метку из далёкого будущего: возраст ограничен с двух сторон
  (`-max_age <= age <= max_age`), а будущая метка свежая только в пределах
  `max_age` (допуск на расхождение часов). Раньше условие `now - stamp <= max_age`
  выполнялось для любого `stamp >= now - max_age`, то есть метка из будущего
  вечно удовлетворяла liveness-пробу и зависший воркер не перезапускался.
- Vision LLM (`workers/classifiers/vision_llm.py`): при отмене корутины
  (`CancelledError` во время `process.communicate()`) дочерний процесс qwen
  теперь убивается, а после `kill()` на таймауте дожидается `wait()` — не
  остаётся ни живого процесса с картинкой атакующего, ни зомби.
- `BrowserManager.get_browser()` закрыт `asyncio.Lock`: два одновременных
  вызова больше не запускают каждый свой Chromium, и неудачный запуск не
  останавливает общий драйвер, убивая браузер соседа.
- В образе были ДВЕ дистрибуции OpenCV вместо одной. `pip list` показывал
  `opencv-python 5.0.0.93` (её тянет ultralytics: `opencv-python!=4.13.0.90,>=4.7.0`)
  и `opencv-python-headless 4.14.0.94` (её тянет easyocr), обе пишут в один
  `cv2/`, и импортировался не тот пакет, который запинен в `requirements.txt`:
  `cv2.__version__` был `5.0.0`. Теперь Dockerfile после установки зависимостей
  удаляет `opencv-python` и переустанавливает headless
  (`--force-reinstall --no-deps`, версия берётся grep'ом из `requirements.txt`,
  пин поднят до `5.0.0.93` — то, что фактически грузилось, и последний релиз).
  Удаление без переустановки ломает `cv2/` (файлы общие), поэтому reinstall
  обязателен. `pip check` теперь пишет «ultralytics requires opencv-python,
  which is not installed» — ожидаемо: ultralytics нужен импортируемый `cv2`,
  headless-сборка его даёт (проверено: YOLO `predict` и `easyocr.readtext`
  работают, ultralytics при predict ничего не доустанавливает).
- `task_id` больше не возвращается в оборот после чистки. Таблица `tasks`
  создаётся с `__table_args__ = {"sqlite_autoincrement": True}`: SQLite хранит
  максимум когда-либо выданного id в `sqlite_sequence` и выдаёт следующий за ним,
  поэтому purge, удаливший самую свежую строку, не отдаёт её id новой задаче, и
  клиент с сохранённым старым id получает 404 вместо своей новой задачи. Один
  `Column(..., autoincrement=True)` AUTOINCREMENT в SQLite не даёт (замерено на
  SQLAlchemy 2.0.23) — нужен именно табличный параметр. Существующая база 1.0.x
  мигрирует в `init_db()`: `ALTER TABLE` AUTOINCREMENT не добавляет, поэтому
  `_migrate_tasks_autoincrement()` в `app/database.py` пересоздаёт таблицу —
  переименовывает старую, снимает уехавшие вместе с ней индексы (иначе
  `ix_tasks_id` занято), создаёт таблицу из модели, переливает строки (это же
  заполняет `sqlite_sequence` максимумом id) и удаляет временную. Список колонок
  берётся из `Task.__table__.columns`, не хардкодом. Если таблицы нет или в её
  DDL уже есть AUTOINCREMENT, функция возвращает `False` и ничего не делает,
  поэтому повторный `init_db()` безопасен.
- `init_db()` больше не падает, когда API и воркер стартуют одновременно на
  свежем томе: создание таблиц и миграция `tasks` идут в одной транзакции
  `BEGIN IMMEDIATE` на одном соединении. Без замка пишущего `create_all` второго
  процесса умирал на `table users already exists` (воспроизведено); теперь он
  ждёт освобождения замка (`busy_timeout` 5 с) и видит уже закоммиченные таблицы.
- `init_db()` дожидается чужой блокировки, а не сдаётся после одной попытки.
  `busy_timeout` ограничивает одну попытку, а миграция во втором процессе может
  идти дольше — проигравший умирал на `database is locked` (замерено в образе:
  `sqlalchemy.exc.OperationalError … database is locked [SQL: BEGIN IMMEDIATE]`
  через 5,01 с), и старт API или воркера прерывался. Тело вынесено в
  `_init_db_once()` без изменений, обёртка `init_db(lock_wait_seconds=60.0)`
  повторяет его каждые 0,5 с, пока в тексте ошибки есть `locked` и не исчерпан
  бюджет; любая другая `OperationalError` (битый файл, том только на чтение)
  пробрасывается сразу.
- `purge_tasks()` отвергает `batch_size < 1` с `ValueError`: `LIMIT 0` в SQLite
  означает «ни одной строки», поэтому чистка молча ничего не делала и рапортовала
  порядок, а `LIMIT -1` снимает ограничение вовсе и возвращает весь бэклог в одну
  долгую транзакцию — ровно то, от чего батчи должны уходить.
- Разовая миграция `auto_vacuum` больше не запускается, когда на томе нет места
  на вторую копию базы: `_has_room_for_vacuum()` в `workers/cleanup.py` сверяет
  `shutil.disk_usage(<каталог базы>).free` с `2 * <размер файла базы>` и при
  нехватке пропускает `VACUUM` с предупреждением, а следующий цикл пробует снова.
  Раньше `VACUUM` падал на середине и повторялся каждый цикл, каждый раз держа
  блокировку записи всё время перестройки: замер в образе — `POST /api/v1/task`
  против удерживаемого замка записи отвечает HTTP 500 через 5,01 с (столько
  длится `busy_timeout`). `wal_checkpoint(TRUNCATE)` выполняется во всех трёх
  ветках. Пустой путь и `:memory:` проверку проходят без чтения ФС.
- Числовые настройки ограничены снизу (`Field(..., ge=...)` в `app/config.py`):
  `max_active_tasks_per_key >= 0`, `cleanup_interval_seconds >= 1`,
  `input_retention_hours >= 0`, `task_retention_days >= 0`. Отрицательная квота
  молча отключала лимит (`create_task` проверяет `if limit > 0`), отрицательный
  срок хранения сдвигал границу чистки `now - retention` в будущее и удалял
  свежие задачи, нулевой интервал запускал чистку на каждом опросе. Границы
  включительные: `max_active_tasks_per_key=0` по-прежнему значит «без лимита».

### Known limitations
- Миграция `tasks` на AUTOINCREMENT продолжает счёт с `max(id)` строк,
  которые есть в таблице. Если до обновления все задачи были удалены вручную,
  прежний максимум взять неоткуда и счёт начнётся с 1.
- Браузерные солверы (reCAPTCHA v2/v3, hCaptcha, Turnstile) в 1.1.0 не решают
  даже демо-страницы; рабочий тип задач — `image_text`. Починка — следующая веха.
- Остановка qwen CLI (`_reap`): `killpg` выполняется, только пока лидер не
  собран. Если CLI завершился раньше потомка, который держит его stdout/stderr,
  этот потомок не убивается. Воркер его не ждёт: ожидание ограничено
  `_REAP_TIMEOUT`, зависания нет, но процесс остаётся жить.

  диска раннера.
